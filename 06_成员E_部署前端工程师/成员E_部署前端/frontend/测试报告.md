## 一、总体结论

**系统可以正常使用**：从「输入投诉文本 → 点击分类 → 展示 Top3 结果 → 写入历史记录」的完整链路跑通，UI 展示结果与后端接口返回**逐位一致（误差 0 个百分点）**；边界校验、异常兜底、防重复提交、移动端适配都做得不错。

**最需要关注的问题是模型"过度自信"**：Top-1 准确率 82.4%，但平均置信度高达 98.3%，界面上会理直气壮地显示「99.3%」，而这个数字并不可信。

## 二、做得好的地方（已验证）

1. **主流程完全正常**：`首页 → 输入 → 开始分类 → Top3 结果卡片`，浏览器实测点击响应约 217ms。
2. **UI 与接口结果零偏差**：同一文本，界面显示「数码3C 49.7% / 电商平台 48.7%」，直连接口返回完全相同。
3. **前后端 18 类标签完全一致**：类别名一字不差（仅展示顺序不同，无功能影响）。
4. **前后端长度限制一致**：都是 10~500 字，客户端拦截 + 服务端二次校验（501 字后端同样 422）。
5. **异常兜底做得很到位**（真实浏览器验证）：
   - 断网 → 「分类失败 / 暂时无法连接分类服务，请检查后端服务是否启动。/ 重新尝试」
   - 30s 超时 → 同上，并出现重试按钮；点击「重新尝试」后恢复正常并展示结果 ✓
   - 后端 500 → 「分类服务返回错误(500)」
6. **防重复提交有效**：注入 1.8s 网络延迟后，加载中连点 4 次**只发出 1 次请求**；加载态显示「正在分析...」。
7. **历史记录持久化正常**：写入 `localStorage.history`，刷新页面后记录仍在，可显示「共 N 条」。
8. **移动端适配正常**：390px 宽度下 `scrollWidth == clientWidth`，无横向溢出。
9. **页面健康**：无 JS 运行时异常、无失败网络请求、控制台无 error。
10. **XSS 防护正常**：输入 `<img src=x onerror=...>` 后 `document.title` 未被篡改，React 默认转义生效。
11. **性能与稳定性优秀**：

    | 指标 | 结果 |
    |---|---|
    | 单次延迟 P50 / P90 / P99 | 113ms / 116ms / 123ms |
    | 10 字 vs 500 字延迟 | 115ms vs 112ms（几乎无差异） |
    | 并发 50 | 全部 200，墙钟 4.9s，约 10 req/s |
    | 连续 60 次 | 成功 60/60 |
    | 同输入重复 20 次 | 结果**完全一致**（确定性推理） |
12. **输入健壮性**：emoji、繁体、全英文、纯标点、零宽字符、控制字符、全角空格、20 万字超长文本，全部不崩溃且返回结构完整。

## 三、问题清单

### 🔴 P1 — 模型置信度严重过度自信（建议优先处理）

**现象**：68 条评测中，Top-1 准确率 82.4%（56/68），但**平均置信度 98.3%**。

- 12 条错误样本，**其中 10 条置信度 > 90%**，错误样本平均置信度 **96.1%**
- 全部 68 条样本中，**Top1 与 Top2 差距小于 10% 的：0 条** —— 说明 softmax 输出极度尖锐，模型从不表达"不确定"
- 实例：
  - 「网约车司机绕路并且态度恶劣」→ **旅游出行 99.8%**（应为共享出行）
  - 「干洗店把羊绒大衣洗坏了」→ **家居日用 99.3%**（应为本地生活）
  - 「4S店保养被强制搭售」→ **家居日用 86.3%**（应为汽车）

**业务影响**：
- 界面直接展示「99.3%」，用户会把它当成事实依据，而实际错误率约 18%
- 前端有一条规则「其余类别置信度低于 30% 不展示」—— 由于没有低置信度输出，**这条规则实际上永远不会触发**，形同虚设
- 界面只显示 Top1/Top2 两个高置信度答案，**掩盖了真实的不确定性**

**建议**：
1. 训练侧：温度缩放（Temperature Scaling）或标签平滑重训，做置信度校准；用 ECE（期望校准误差）评估而不只看准确率
2. 训练侧：检查是否因增强数据（23107 条合成 / 30000 总，占比 77%）导致过拟合到模板化表达、softmax 过度尖锐
3. 产品侧：文案改为"模型判断倾向"而非直接给概率；或在 UI 上明确标注"置信度为模型自评，非正确率保证"

### 🟠 P2 — 类别体系本身存在重叠，导致"电商平台"变成吸引子

各类别命中情况（每类 4 条）：

| 类别 | 命中 | 典型错误 |
|---|---|---|
| 电商平台 / 物流快递 / 旅游出行 / 金融支付 / 教育 / 数码3C / 通讯运营商 / 医疗健康 / 婚恋交友 / 房产家装 | 4/4 | — |
| 服饰鞋包 | **1/4** | 羽绒服跑绒→电商平台 96.7%；假鞋→电商平台 99.3%；直播买包→电商平台 99.3% |
| 家居日用 | **1/4** | 家具尺寸不符→房产家装 99.1%；床垫塌陷→房产家装 99.0%；锅具掉渣→电商平台 91.4% |
| 本地生活 | 2/4 | 干洗店洗坏衣服→家居日用 99.3%；美发店会员卡→医疗健康 95.8% |
| 汽车 | 3/4 | 4S店搭售保养→家居日用 86.3% |
| 共享出行 | 3/4 | 网约车绕路→旅游出行 99.8% |
| 影音娱乐 | 3/4 | 直播打赏→游戏 87.7% |
| 母婴食品 | 3/4 | 外卖吃出异物→本地生活 98.8% |

**关键观察**：`电商平台` 的类说明是「涉及商品购买、退换货、商家服务等投诉」，而 `服饰鞋包` 是「服装、鞋包质量与售后」—— 两者语义**天然重叠**。凡是"网购 + 质量 + 退货"的投诉，都同时满足两个类的定义，模型只能靠数据分布去猜，结果被样本量更大的 `电商平台` 吸走。

**需要说明的是**：部分"错误"是我的主观标注与项目标签体系不同所致（例如"外卖吃出异物"归到 `本地生活` 其实完全合理）。但 `网约车→旅游出行 99.8%`、`干洗店→家居日用 99.3%`、`美发卡→医疗健康 95.8%` 这类属于明显不合理。

**建议**：
1. 审查 18 类的定义边界，把"购买渠道"（电商平台）和"商品品类"（服饰鞋包）的判定优先级写清楚，例如约定"优先按商品/服务品类，除非投诉主体是平台规则本身"
2. 检查训练集各类样本量是否均衡，特别是 `服饰鞋包`、`家居日用`、`本地生活` 是否被 `电商平台` 挤占
3. 补充这几类的困难样本再训练

### 🟡 P3 — 界面展示的数据集统计前后不自洽

`统计数据页 / 模型介绍页` 的 `DATASET_STATS`：

- 清洗后：**8950** 条
- 但 训练真实 6893 + 验证 855 + 测试 877 = **8625** 条
- **差 325 条去向不明**

（其余项自洽：30000 = 6893 + 23107 ✓；增强比例 23107/30000 = 0.77 ✓）

**建议**：核对这 325 条是丢弃了、还是统计口径不同，并在页面上说明。答辩/演示时被问到会很难解释。

### 🟡 P4 — `/health` 健康检查接口前端拿不到

- 后端有 `GET /health` → `{"status":"ok","model_loaded":true}`（8000 端口直连正常）
- 但 Vite 只代理 `/api`，通过前端入口访问 `/health` 会被 SPA 兜底返回 **index.html，且状态码 200**
- 后果：如果前端将来加"服务状态检查"（页面上那个「模型已就绪」标记），用 `res.ok` 判断会**永远显示正常**，因为 HTML 也是 200
- `/api/health` 则返回 404

**建议**：后端把健康检查挪到 `/api/health`，或在 Vite 代理里加上 `/health`。

### 🟡 P5 — 后端端口与 CORS 对局域网完全开放

- `http://192.168.34.172:8000/docs`（Swagger UI）局域网内任何机器可直接访问
- `Access-Control-Allow-Origin: *`，且 `Access-Control-Allow-Methods` 允许全部方法
- 局域网内任何人可以绕过前端直接刷接口、消耗推理算力

**建议**：演示环境可接受；正式部署时把 8000 端口改为只监听 `127.0.0.1`（只走 5173 代理），CORS 收窄为具体来源。

### 🔵 P6 — 若干细节问题

1. **前端 API 地址兜底写法有隐患**：`VITE_API_BASE_URL ?? 'http://localhost:8000'`，而 `.env` 中该值为**空字符串**。空字符串不会被 `??` 兜底，所以实际走的是相对路径 `/api`（**恰好正确**）。但如果有人把 `.env` 改成 `http://localhost:8000`，局域网其他电脑访问时浏览器会去请求**自己本机的 8000 端口**而失败。建议改成 `|| ` 或显式判空，并加注释说明"留空 = 走 Vite 代理"。
2. **空输入时「开始分类」按钮为禁用态，但没有任何文字说明**（实测点击无反应、无提示）。建议加 `title` 提示或占位文案。
3. **超时提示文案不准确**：实际是 30 秒超时，却提示「暂时无法连接分类服务，请检查后端服务是否启动」。建议区分"连接失败"和"请求超时"。
4. **错误文案不统一**：直接调接口时，空字符串返回 pydantic 英文 `String should have at least 1 character`，而纯空格返回中文「投诉内容过短, 请补充到 10 字以上」。前端因为有自己的校验所以看不到，但对接口调用方不友好。
5. **前端类别顺序与后端返回顺序不同**：后端按概率降序返回，前端 `config/categories.ts` 用自己的固定顺序。无功能影响，仅提示注意。

## 四、测试过程中"疑似缺陷"但复核后排除的项

透明起见，列出我一开始判为失败、复核后确认是**测试用例本身问题**的项：

| 现象 | 复核结论 |
|---|---|
| 空文本点击"无任何提示" | 按钮在空输入时是 `disabled`，属正常设计，非缺陷 |
| 连点 3 次发出 3 次请求 | 请求仅 ~150ms，三次点击是**三次真实的顺序分类**。注入 1.8s 延迟后复测：加载中连点 4 次只发 1 次 → 防重复提交正常 |
| 501 字返回 422 | 后端上限也是 500，与前端一致，属正确行为 |
| 缺少 CORS 响应头 | 未带 `Origin` 头时本就不返回；带上后返回 `ACAO: *`，CORS 正常 |
| GET 请求失败 | 接口只注册了 POST，返回 405 属正确行为 |
